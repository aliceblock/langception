# The offline OCR Engine's larger tiers arrive as first-use Model Pack downloads

ADR-0005 shipped all seven model files inside the installer ("packaging-time (not first-run) download discipline") so the bundled engine needed zero setup — but the Small and Medium recognizers alone put ~170 MB of ONNX into every installer for tiers most users never select: Windows OCR is the default engine, and a bundled-engine selection that names no tier lands on Small. We decided to keep only the sidecar binary (statically linking ONNX Runtime, ~29 MB) and the Tiny tier's files (~6 MB) in the bundle and deliver the rest as Model Packs — the Small set (~31 MB), the Medium set (~139 MB), and the Korean recognizer set (~13.5 MB) — downloaded when an OCR Engine selection needs them, from URLs and hashes pinned in a models manifest shipped with each release (GitHub Releases assets primary, the pinned Hugging Face/ModelScope URLs fallback — the same pins the packaging fetch script carries today), each pack verified by hash before use. The download is lazy — on selection, never at launch — and the selection saves immediately: passes surface the not-ready state through the existing sidecar spawn-failure/recovery-notice machinery until the pack lands, never falling back to Windows OCR on their own. Downloaded packs live beside the exe in portable mode and in %LOCALAPPDATA% for installs, and nothing deletes a pack automatically — an explicit Engines-tab button removes packs the current selection does not use. Tiny stays bundled so the offline story ("needs no OS language packs") keeps an offline baseline for English and Chinese with no network at all; Japanese still needs the Small set, because the tiny+Japanese substitution already loads Small's files.

## Considered options

- **Bundle Tiny + Small** (~70 MB of resources): keeps the default-tier contract fully offline and a Japanese Tiny selection working with no download — rejected against this goal: the point is a smaller installer, and Small is 31 of those 70 MB.
- **Bundle nothing but the sidecar binary** (~29 MB): smallest possible, but a fresh machine without OS language packs and no network has no OCR at all; Tiny costs ~6 MB and preserves a partial offline guarantee.
- **Defer the sidecar binary too**: rejected — deferring an executable turns this feature into an updater problem (signature, trust, bootstrap) of its own, and the binary is required for any deferred model to run.
- **Eager first-launch download / auto-delete of unused packs / byte-resume**: rejected in the design session — downloads happen only as a consequence of a selection; deleting a metered-connection user's 139 MB Medium pack because they toggled tiers is a decision made for them; a canceled download re-fetches from zero, costing at worst one ~139 MB re-download.

## Consequences

- ADR-0005's packaging-time consequence is amended, not rewritten: Tiny's files and hashes still flow through the packaging fetch script; the Small/Medium/Korean sets inherit the same pinned-URL-plus-hash discipline, with the hash check moved to download time on the user's machine.
- The models manifest ships inside the app and is never fetched at runtime: a release's model set is exactly the set that release tested, and bumping a model means a new manifest in the next release — no second network dependency ahead of the downloads themselves.
- A tier selection whose pack is missing stays honored as selected: the loop reports "loading" through the recovery-notice path until the pack is ready; only the user switching engines switches engines.
- The pack resolver consults the effective selection, not the literal one: Japanese + Tiny downloads the Small set (the substitution already runs Small's files), and Korean + Small/Medium pulls the tier's detection file plus the Korean recognizer set.
- The glossary's `Model Tier` entry drops its "bundled" claim and `Model Pack` names the download unit; "the bundled engine" in packaging-level docs names the Tiny baseline from here on.
- The NSIS uninstaller leaves downloaded packs in %LOCALAPPDATA% like any app data; the Engines-tab delete button is the in-app cleanup surface.
